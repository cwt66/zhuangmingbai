## 1. 五分钟跑起来

```bash
git clone <仓库地址> && cd zhuangmingbai

# 审计引擎零第三方依赖，可先单独验证
python3 src/pipeline.py        # 产出 out/audit_report.{md,html} / audit_result.json

# Web Demo 需要三个包
python3 -m pip install -r requirements.txt
python3 -m uvicorn main:app --host 127.0.0.1 --port 8000
```

打开 `http://127.0.0.1:8000`。

| 路径 | 作用 |
|---|---|
| `/` | 上传页，附三份样例 CSV 下载 |
| `POST /audit` | 上传 2–4 份 CSV，返回可打印报告 |
| `/demo` | 用三份样例一键跑完整流程 |
| `/real` | 用仓库内一份 127 行真实单据跑审计 |
| `/perceive` | 图片/PDF/Excel → 识别 → 审计（GET 表单，POST 执行） |
| `POST /vision/audit` | 本地 OCR 草稿校对后的 CSV → 审计 |
| `POST /feedback` | 报告页反馈（写入 RDS/SQLite） |
| `/review` | 解析校对台（改数自动重算） |
| `/inquiry` | 问询单：把结论转成可以直接发给报价方的问句 |
| `/history` | 审计历史（RDS/SQLite 落库凭证） |
| `/report/{id}` | 单次审计摘要回看 |
| `/health` | 探活：db / cache / llm 三项状态 |
| `/api/demo` | 样例结果的 JSON 版 |
| `POST /api/audit` | 程序化审计：返回 audit_id、fingerprint、documents、ai 解读 |
| `GET /api/audits` | 最近审计列表 |
| `/samples/{name}` | 下载样例 CSV |

**注意**：`/audit` 至少要 2 份报价单。漏项金额是拿同批报价横向参照估的，
只有 1 份时没有参照，引擎会拒绝而不是瞎给一个数。

### 1.1 环境变量（全部可选，不配也能跑）

| 变量 | 不配时的行为 |
|---|---|
| `DATABASE_URL` | 用 `data/state.db`（SQLite） |
| `REDIS_URL` | 用进程内缓存；`/health` 显示 `kind=memory` |
| `MAAS_API_KEY` | 报告「解读」由规则模板生成，页面明确标注 |
| `MAAS_BASE_URL` / `MAAS_TEXT_MODEL` | 默认 `https://api.modelarts-maas.com/v1` / `DeepSeek-V3`（以控制台为准） |
| `PERCEPTION_PROVIDER` | 默认 `auto`：MaaS Key → `maas`；有 AK/SK → `ocr_table`；macOS → `vision`；结构化文件自动走 `file` |
| `VISION_OCR_BIN` | 默认 `scripts/bin/vision_ocr`；可指向自编译二进制 |
| `RATE_LIMIT` | 默认 60 次/分钟/IP；设 0 关闭 |

### 1.1.1 本地 OCR（macOS，可选）

```bash
bash scripts/build_vision_ocr.sh
python3 scripts/ocr_vision.py 报价单.jpg --out out/quote_vision.csv
```

- 图片不出本机；输出标准 8 列 CSV，可直接 `/audit` 或 `/perceive` 继续。
- `/perceive` 若判断需核对比例 >35%，会停下来让你先改 CSV，再 POST `/vision/audit`。
- 中文 OCR 有错字，**不要把它当全自动识别**；critic 会标出缺字段/量价不符/低置信。

### 1.2 一条命令自检

```bash
bash scripts/check_all.sh
```

会跑 97 个单测、覆盖率、黄金标注、消融、注入、冻结指纹、隐私扫描。
全绿再提交，换机器复现也用它。

## 2. 输入格式

CSV，UTF-8（带不带 BOM 都行），**首行必须是表头**。

| 列名 | 必填 | 说明 |
|---|---|---|
| `序号` | 否 | 原表行号。留空则按物理行序自动编号，报告里引用的就是它 |
| `项目名称` | **是** | 工序名。这是对齐到工序轴的唯一依据 |
| `规格工艺` | 否 | 规格、做法、分区。**分区标注写在这里**，格式 `分区：主卧`，用于重复计价判定 |
| `单位` | 否 | m2 / m / 项 / 套 / 只 / 根 / 袋 … 用于口径校验 |
| `数量` | 否 | 数字，可带千分位逗号 |
| `单价` | 否 | 数字 |
| `合价` | 否 | 数字。**漏项与重复的金额都以它为准**，缺失按 0 计 |
| `备注` | 否 | 参与文本证据判定。**否定语境在此识别**：`不含垃圾外运` 不算已含 |

最小可用：只有 `项目名称` 和 `合价` 两列也能跑，但漏项、口径两类结论会明显变少。

示例：

```csv
序号,项目名称,规格工艺,单位,数量,单价,合价,备注
1,铺墙砖（300*450）,分区：卫生间,m2,22,64,1408,
2,老房拆旧（暂估按实结算）,分区：土建,项,1,2200,2200,含拆除，不含垃圾外运
```

### 三份样例

`data/samples/company_a.csv`（规范型）、`company_b.csv`（低价引流型）、
`company_c.csv`（高价项全型）——同一个 80㎡ 老房、三家报价，用于演示"最低价不等于最低成本"。

**必须三份一起跑**。只跑 A+B 时 B 的漏项参照会变，数字与文档对不上。

## 3. 错误码与常见问题

| HTTP | 提示 | 原因与处理 |
|---|---|---|
| 400 | 没有收到文件 | 没选文件 |
| 400 | 至少需要 2 份报价单 | 只传了 1 份。漏项参照需要横向比较 |
| 400 | 最多 4 份 | 一次超过 4 份，分批 |
| 400 | 《x》超过 4MB | 单文件超限 |
| 400 | 《x》是空文件 | 0 字节 |
| 400 | 没有解析到行项 | 表头不是中文列名，或文件里只有表头没有数据 |
| 500 | 解析或计算过程中出错 | 通常是数字列里混了非数字字符，看 detail |
| 404 | not found | 样例或真实单据文件不在仓库里 |

**中文乱码**：用 Excel 另存为「CSV UTF-8」。GBK 编码会读成乱码，表现为"没有解析到行项"。

**金额算不对**：检查 `合价` 列是否为空。引擎不做 `数量×单价` 的推算，
因为真实报价单里这两者经常不一致——那本身就是一条要被报出来的口径风险（R8 算术校验）。

## 4. 判定逻辑（三条规则，都可人工审阅）

引擎只输出三类结论，且每条都带行号、基准、公式、置信度。

### 4.1 漏项（R1）

```
模板必做项（老房 38 项 / 新房 25 项）
  − 概念对齐命中的项
  − 文本证据词命中的项
  = 漏项
```

**为什么要有第二路证据**：真实报价单是复合行。`墙面基础处理+批嵌砂光` 一行同时含
"基层处理"和"批腻子"，若只按概念 1:1 对齐，批腻子会被判成漏项。
证据词表在 `data/coverage_v0.json`，每个词都能在原表里指认。

**否定语境**：命中前先看词前 6 字。`含拆除，不含垃圾外运` 里"垃圾外运"出现了，
但前面是"不含"，不算已含。这条踩过坑，B 公司的备注就是这句话。

**分档**：`墙固 / 界面剂 / 底漆` 这类常被打包进复合行的，只有在复合工序确实存在、
而它本身没单列时，才降为「建议复核」。复合工序也不存在 → 仍是确定漏项。

### 4.2 重复计价（R2 / R3）

按「概念 + 分区」分组，同一组内多行才可能是重复。

组内先比**变体**：行名去掉概念正式名后剩下的部分。

- `墙面找平` 与 `墙面找平` → 残差都为空 → 是重复
- `墙面防水` 与 `地面防水` → 残差不同 → 不同部位，**直接排除**

只剥正式名、不剥别名——别名本身带部位词（顶面涂料/墙面涂料都是 topcoat 的别名），
剥了会把顶面和墙面判成重复。

### 4.3 口径风险（R4 / R6–R12）

| 规则 | 查什么 |
|---|---|
| R4 | 模糊措辞：按实结算、暂估、据实、另计 |
| R6 | 单位异常：该按面积报的按"项"报 |
| R8 | 算术校验：\|合价 − 数量×单价\| > 1 |
| R9 | 数量口径：面积类工序按"项"报价，工程量不可核 |
| R10 | 费率类：管理费/税金的计费基数不明 |
| R11 | 规格缺失：无品牌无型号无工艺 |
| R12 | 防水高度：卫生间墙面防水是否做到 1.8m |

### 4.4 置信度与三档处置

```
confidence = 0.4×规则强度 + 0.2×解析质量 + 0.2×对齐置信度 + 0.2×(模板命中 ? 1 : 0.5)
```

| 档位 | 阈值 | 处置 |
|---|---|---|
| 自动通过 | ≥ 0.90 | 计入核减金额 / 确定性漏项 |
| 建议复核 | 0.60–0.90 | 标黄，写明"为什么不确定" |
| 转人工 | < 0.60 | 标灰，只提示"此处需人工确认" |

**低置信度结论不进金额。** 宁可少报，不可错报——这是设计的第一原则。

## 5. 改代码的入口

| 想改什么 | 改哪里 |
|---|---|
| 常见叫法（别名） | `data/ontology_v0.json` 的 `a` 字段 |
| 漏项证据词 | `data/coverage_v0.json` 的 `evidence` |
| 必做项清单 | `data/templates_v0.json` |
| 规则强度/包含对 | `data/rules_v0.json` |
| 判定算法 | `src/pipeline.py`（`find_missing` / `find_duplicates` / `find_vague` …） |
| 报告样式 | `build_markdown` / `build_html` |

改完必须跑这三条，数字不能变：

```bash
python3 src/pipeline.py                 # 合成三单：A 400 / B 22,164 / C 3,168
python3 eval/eval_alignment.py          # 覆盖率 83.3%
python3 -c "import main"                # Web 层可导入
```

回归线写在 commit message 里。任何改动导致这三个数变化，都要说明为什么。

## 7. 已知限制

1. **照片解析依赖云服务**。`file` provider 覆盖 CSV/XLSX/PDF 文本层；照片需要
   MaaS Qwen-VL 或华为云表格识别。已实现并有实测记录（OCR 38 行算术全过），
   但当前账号的 OCR 额度受限，真实照片端到端要等额度恢复。
2. **不判断贵不贵**。没有价格库，也不打算有——判断价格合理性会引入数据合规问题。
3. **模板是通用清单**，不按房型定制。有些项（如墙固）行业上是否必做并不统一，
   这类会降为「建议复核」而不是判成漏项。
4. **n 很小**。2 份完整黄金标注、5 份真实单据；只作存在性证明，不外推总体召回率。
5. **置信度是证据强度分，不是概率**。不做 ECE / risk-coverage 声称。
6. **云上实例状态以账号控制台为准**。代码已接入 RDS/Redis，未开通时自动降级，
   `/health` 会如实显示 `sqlite` / `memory`，不假装已上云。
