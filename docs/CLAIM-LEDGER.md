# 主张台账：让「我们说过的话」也进 CI

> 口径：2026-11-07 ｜ 25 条主张 ｜ ① 18 / ② 4 / ③ 3 ｜ 撤回档案 13 条 + 预测 MISS 3 条
> 一键复算：`python3 scripts/claim_ledger.py --self-test`

---

## 一、为什么要有这一层

项目此前已经有交付门、负向知识库、红队自测、规则活性变异测试。
但它们管的都是同一件事：**引擎输出对不对**。

还有一类东西从来没人管：**我们对外说的话对不对**。

一份材料里写着「243 个测试」「119 概念 / 388 别名」「15 步自检」
「判定引擎 1,248 行」。代码一改，这些数字就悄悄过期。
评委不会去数，我们自己也不会——直到某天同一份材料里同时出现
145 和 221 两个测试数，才发现它已经漂了很久。

**一个连自己的宣传语都没验过的项目，凭什么要求评委相信它的审计报告？**

方法不是自己想的。华为云社区 2026-10-03 那篇
[《一个会自我审计的系统：可信度是怎样被公开建造的》](https://bbs.huaweicloud.cn/blogs/494747)
给了 6 条可操作清单：

| # | 清单条目 | 此前状态 |
|---|---|---|
| 1 | **给每条断言配上产生它的命令**；写不出命令的降级成「推测」 | ❌ 本轮补上 |
| 2 | CI 里重跑断言，断言坏了徽章要红 | ✅ `check_all.sh` 第 16 步 |
| 3 | 给判据加双向测试（该拒绝的拒绝、该通过的通过） | ✅ 规则活性已有；台账也补了 |
| 4 | 拿变异测试撞自己的门禁 | ✅ `eval/rule_liveness.py` |
| 5 | 建一个缺陷清单文件 | ✅ `docs/RULE-BLIND-SPOTS.md`；本轮补撤回档案 |
| 6 | **把证据分档写进结论里**，别让「我看过」和「我跑过」长得一样 | ❌ 本轮补上 |

> 那篇文章的一句话是这套东西的地基：
> **系统的可信度不是测出来的，是公开建造的——你把自己做错的部分留在台面上，别人能查，那才叫可信。**

## 二、三件可执行的事

### 1. 台账：`value` 不是判据，`observed` 才是

`data/claims_v0.json` 里每条主张长这样：

```json
{
  "id": "C01",
  "text": "单元测试 312 个",
  "value": "330",
  "tier": "ran",
  "probe": "tests_count",
  "command": "python3 -m unittest discover -s tests",
  "occurrences": [{"file": "README.md", "pattern": "tests-{v}-brightgreen"}]
}
```

- `value` 是**公开宣称的值**（我们要对外负责的那句话）。
- `probe` 是校验器当场执行的探针，从源头重算出 `observed`。
  **台账里写自己是对的，不算证据**——这跟「模型自报置信度」是同一个错误。
- `occurrences` 里的 `{v}` 会替换成 `value`，反查文档里这句话还在不在。
  于是两个方向都锁住了：改了文档没改台账 → 找不到；改了代码没改文档 → 数字对不上。
- `tests_count` 探针**刻意再跑一次 unittest**，不复用自检第 2 步的输出。
  证据必须由产生它的命令当场跑出来，不能借别人的结果盖章。

### 2. 证据分档：① > ② > ③

| 档 | 含义 | 条数 | 能不能写「已验证」 |
|---|---|---:|---|
| ① `ran` | 校验器当场执行命令、从源头重算 | 18 | ✅ |
| ② `read` | 值来自命令生成的产物，本次未独立重算 | 4 | ⚠️ 只能写「读档一致」 |
| ③ `declared` | 写不出命令的边界声明 / 否定式主张 | 3 | ❌ **只作声明** |

三条 ③ 档故意留着，不许伪装成已验证：

| ID | 声明 | 为什么写不出命令 |
|---|---|---|
| C17 | 黄金标注 n=2，只作存在性证明 | 样本量小是事实，但「不外推」是一条判断，不是一条命令 |
| C18 | 鲲鹏未实测、昇腾 NPU 未涉及 | 无法用命令证明「没做过」 |
| C19 | MaaS Key / OCR 服务未开通 | 账号状态以控制台为准，本地命令证明不了 |

**② 档在干净 clone 里会显示「待复算」**——`out/ablation.md` / `out/rule_liveness.md`
是 `check_all.sh` 第 5、15 步生成的产物，不入库。独立跑台账时它们不存在，
校验器如实报「待复算」，不算通过，也不算失败。这比悄悄复用一份旧产物诚实。

> 文章原话：`① 跑出过结果 > ② 读过原文 > ③ 只按元数据判`，
> **低于 ③ 的判断不进档案**。这条约束很痛——它逼你承认「我没读」，
> 而不是把「没读」包装成「读过了」。

#### 一次真实的降级：CI 第一个抓到的是我们自己

台账上线当天推到 GitHub，CI（`ubuntu-latest`，**x86_64**）在第 16 步报
（[Actions run 42372612688](https://github.com/cwt66/zhuangmingbai/actions/runs/42372612688)，
`conclusion=failure`，可核对）：

```
C14 宣称 arm64，实测 x86_64 —— 数字漂了
```

复查发现是**台账自己的错**：C14 说的是「**开发机** arm64」，
却让探针用 `platform.machine()` 当场复算——等于用另一台机器的架构
去给开发机盖章。处理不是把探针改成永远返回 `arm64`（那才是造假），
而是**把 C14 从 ① 降为 ②**：改读采集时写入的 `data/dev_environment_v0.json`，
并在撤回档案记 H11 留案。于是档位从 ① 14 / ② 2 / ③ 3 变成
**① 13 / ② 3 / ③ 3**——数字变难看了，但它是对的。

> 一个刚上线的判据，第一个抓到的是自己的口径错误。
> 这比它抓到别人更让人放心：**它没有豁免权。**

### 3. 撤回档案：被撤回的结论不删

`data/claim_history_v0.json` 记 13 条，分六类：

| 类别 | 例子 |
|---|---|
| `withdrawn` | 测试数 145→205→221→224→264；自检 12→17 步；OBS「永久」改口 |
| `false_positive` | 冻结基线「5/5 已入库」实为 clone 只有 3/5；10 页复验页 PDF 全是同一页 |
| `false_alarm` | 把 `not subscribed` 误判成「签名实现写错了」 |
| `known_unfixed` | 红队 A3「㎡ 写成 m」得手，不硬修，配一条断言它拦不住的测试 |
| `missed_prediction` | 「13 条规则都在起作用」被第一次变异测试 18/47 当场证伪 |

另有 `predictions` 3 条，**`miss: true` 永久保留**：
预测 MISS 不许因为后来修好了就从档案里消失。

档案的 SHA-256 指纹写在台账 `meta.history_digest` 里。
**删一条、改一个字，第 16 步立刻红**；确需增补必须 `--update-digest`
并写明原因——改档案本身也留痕。

## 三、双向断言与故障注入

`python3 scripts/claim_ledger.py --self-test` 同时验两件事：

| 用例 | 期望 | 实际 |
|---|---|---|
| 干净台账 | **PASS** | PASS |
| 把 C01 宣称数字改错 | FAIL | FAIL |
| 模拟文档漂移（出现位置找不到） | FAIL | FAIL |
| ① 档主张摘掉探针 | FAIL | FAIL |
| 把 ③ 档偷偷升成 ① 档（不给命令） | FAIL | FAIL |
| 删掉一条被撤回的结论 | FAIL | FAIL |
| 抹掉预测 MISS | FAIL | FAIL |

> 一个永远报错的校验器，和一个永远放行的校验器，一样没用。
> 所以「干净必须 PASS」和「故障必须 FAIL」两条缺一不可。

同一个姿势也用在 Skills 规范校验器上：
`python3 scripts/verify_skill_spec.py --self-test`（1 正向 + 6 故障，20/20 项）。

## 四、怎么加一条新主张

1. 在 `data/claims_v0.json` 加一条，写清 `text` / `value` / `occurrences`。
2. **先问：能写出产生它的命令吗？** 能 → `tier: ran`，在 `scripts/claim_ledger.py`
   的 `PROBES` 里加一个探针；只能读产物 → `read`；写不出 → `declared`，进欠账清单。
3. 把这句话写进 README / 答辩材料，并确保 `occurrences` 的 `{v}` 模板能匹配到。
4. 跑 `python3 scripts/claim_ledger.py --self-test`。红了就改，别改判据去迁就它。
5. 撤回过的主张进 `claim_history_v0.json`，然后 `--update-digest`。

**不许做的事**：把 ③ 档换个说法写成「已验证」；为了让报告好看删掉欠账；
把一条失败的故障注入改成「不适用」；改 `value` 去迁就 `observed` 而不改文档。

## 五、这套东西证明不了什么（主动交代）

- 它证明「**材料与代码一致**」，不证明「**结论是对的**」。
  判定正确性由黄金标注、消融、注入、交付门、红队各自负责，别把两件事混为一谈。
- ③ 档三条依然是声明，没有任何独立证据。评委要追问，就照实说「这条没法复算」。
- 撤回档案防的是**无意丢失与事后美化**，不是防恶意篡改：
  有人同时改档案和台账指纹，仍能骗过校验器。这是本地文件的信任边界，不装成防篡改系统。
- 探针自己写错了，台账会跟着一起错。所以 `tests/test_claim_ledger.py`
  用桩观察值单独测**校验器逻辑**，与探针正确性分开验——
  这也只是降低风险，不是消除风险。
- 华为云 Skills 规范符合性是 20/20 项**结构 + 文档 + 功能**检查，
  不等于「这个 Skill 好用」，更不等于「通过了华为官方认证」。

### 5.1 台账管不到的两处，本轮补上——但它们**不算 ① 档**

上一轮之后又发现两个缝，都是「我们说过的话没人管」的变体：

| 缝 | 为什么 ① 档管不了 | 补法 | 由谁保证 |
|---|---|---|---|
| **评委拿到的是仓库外的 `国奖提交包/`**（55 份 md、几十处数字、commit hash、sha256 清单）。CI 的 checkout 里根本没有它 | 探针在 CI 上跑不出值；**写不出命令的值不许伪装成当场复算** | `scripts/verify_package_numbers.py`：查旧值残留、当前值覆盖、HEAD 一致性、sha256 清单逐条复算；报告写进提交包 `09_证据附录/` | 本地 ② 档工具，不进 `check_all.sh` |
| **「别人 clone 下来也是绿的」** 之前靠人工记得跑一次。H05 就是这么翻车的：本地 5/5 冻结基线、clone 只有 3/5 | 把「clone 自己 → 跑 check_all」塞进 `check_all.sh` 会**无限递归** | `scripts/verify_clean_clone.py` 从 HEAD 建干净 clone 跑全量自检（11 项检查 / 207 文件 / 冻结基线 5/5）；CI 加**第二个独立 job** `clean-clone`，报告上传 artifact | CI job，不占一步自检编号 |

两个脚本都带**双向断言**：`--self-test` 分别跑 6 例和 5 例故障注入，
干净必须 PASS、坏输入必须 FAIL；另有 10 个单测锁住它们不退化。

**不进 ① 档不是免责，是把它放在真能被复算的地方。**
一个在 CI 上永远「待复算」的探针，硬塞进台账只会换来一个假绿勾；
单列出来、写清由谁保证、把证据留在评委能翻到的地方，才叫交代。

反过来，能当场算出来的就要老实收进来：本轮新增的
**C20「华为云失效矩阵 9 个实验全过」** 是 ① 档，探针直接跑
`eval/cloud_failure_matrix.py --self-test --json`，接进 `check_all.sh` 第 17 步。
所以**那一轮结束时**档位是 **① 14 / ② 3 / ③ 3、共 20 条**——
不是因为又写了句漂亮话，是因为「云依赖挂了会怎样」这句承诺第一次能被跑出来。
（这一段记录的是 C20 当时的值，按纪律不随本轮口径回填。）
顺带说一句：提交包检查器第一次跑把 `11/15`（日期）和 `第 5、15 步`（步骤编号）
都误判成旧值，还差点逼我们删掉「以前写着 243 个测试」这类诚实叙述——
**误报率决定一套判据能活多久**，所以收窄了正则并给历史叙述留了可追溯的豁免。

### 5.2 一条新证据，不许顺手洗掉一条旧欠账

本轮新增 **C21「跨环境判定确定性 12 个变体全过」**，① 档，
探针跑 `eval/determinism_matrix.py --self-test --json`，接进自检第 18 步。
档位因此变成 **① 18 / ② 4 / ③ 3、共 25 条**。

这里有个很诱人的动作：既然 arm64 与 x86_64 判定指纹一致，
是不是可以把 **C18「鲲鹏实例未实测、昇腾 NPU 未涉及」** 升级成「已验证」？
**不行，而且我们把它做成了判据的一部分。**

| 约束 | 落地方式 |
|---|---|
| 存档必须自带三条边界声明 | `data/determinism_arm64_v0.json` 的 `declares` 少任何一条，`evaluate()` 直接 FAIL；双向断言里专门有一例「抹掉鲲鹏声明 → 必须 FAIL」 |
| 不许拿别处的结果冒充 arm64 存档 | 存档 `reference.machine != "arm64"` → FAIL |
| 不许把「同架构复算」说成「跨指令集」 | 报告逐次打印 `跨指令集比对：是 / 否(同架构复算)`；本机 arm64 只能得到「否」 |
| 跨架构那一半由谁保证 | GitHub Actions 第三个 job `determinism`：x86_64 + Python 3.10/3.11/3.12/3.13 空 venv，不装 `requirements.txt` |

所以 C18 **仍是 ③ 档声明**，③ 档欠账依旧是 3 条，没有少。
这套分档如果不能拦住「对自己有利的证据」，它就不值得写进材料。

另一个诚实边界：提交包数字检查器只抓**结构性旧值**（243 测试、15 步、
引擎行数、更早的档位组合），并不追着每一轮的旧档位打。
理由是上一轮它误伤过 `11/15` 日期和「以前写着 243 个测试」这类诚实叙述——
**一个会逼人删掉历史记录的判据，比数字漂移更危险**。
每轮档位变化由台账自己（`data/claims_v0.json` + 撤回档案）负责，不靠正则追杀。

### 5.3 判据被流程修正的一次（不藏起来）

把最终交付 zip 放进 GitHub 仓库时撞到一个自相矛盾：
提交包是在 commit `X` 生成的，之后为了把 zip 本身推上去，必然再产生一个
同步 commit `Y`；而提交包数字检查器原先要求「材料里的 hash == 当前 HEAD」，
于是**刚生成的包立刻被自己判成过期**。

这不是数字漂移，是判据的设计缺陷：它假设「生成」和「上传」是同一次提交。
处理方式不是把 hash 改掉或把断言删掉：

- `release_heads()` 认可快照 hash 落在最近 3 个祖先里，报告里写明
  「发布快照 commit `X` … 当前 HEAD `Y`，相差 N 个同步提交」；
- 任何**无关** hash 仍必须 FAIL，原有的 `tamper_head` 故障注入保留；
- 新增一例正向断言「发布快照是 HEAD~1 → PASS」，`--self-test` 由 6 例变 7 例；
- 处置范围与理由写进 `docs/GitHub上传范围与脱敏边界.md`，可复算。

判据可以改，但**改动必须留下为什么改、谁在看着它、坏输入还会不会被拒**。
否则「修判据」和「放宽判据」就分不清了。

**当天它又抓到自己一次。** `d3564fc` 推上去后，CI 的 `check` job 红，
`clean-clone` 与四个 `determinism` 全绿。差别只有一个：`check` 用
`actions/checkout@v4` 默认的 `fetch-depth=1`，浅克隆里只有 1 个 commit，
`HEAD~1` 根本不存在——于是新增的那例「HEAD~1 正向断言」构造不出来，
自检从 7 例变 6 例，单测按 7 例断言就红了。
`clean-clone` 因为写了 `fetch-depth: 0`，有完整历史，所以绿。

修法不是给 `check` 补一个 `fetch-depth: 0` 了事（那是改环境迁就判据），
而是把「从候选里挑发布快照」抽成纯函数 `select_release_head(heads, texts)`：
`scan()` 照常读 git，双向断言则直接用构造好的候选列表，
**判据不再隐含依赖仓库历史深度**。本地用 `git clone --depth 1` 复现后验证：
浅克隆里仍是 7 例、344 tests OK。
一个只在「历史完整的机器上」才跑得全的判据，和「只在自己机器上绿」没有区别。

### 5.4 最后一环：评委第一眼看到的那一页

前四轮把「代码里的数字」「提交包里的数字」「别人 clone 下来的结果」
「云依赖挂了会怎样」「跨环境是否确定」全接进了自检。
2026-11-09 重读工作流时发现**展示面没人管**：线上评委复验页与仓库外 HTML
字节一致，内容却是 11-05 的**历史存证**：`243 测试 / 15 步 / 写死 commit c56b706`，
而当时已是 `298 测试 / 18 步 / 2aa018f`。README、台账、提交包、CI 全绿，
只有评委手里那一份悄悄过期。

`scripts/verify_showcase.py` 把当前版展示页住进 `deliverables/`，
与台账 **C22** 绑定，接进自检第 19 步：

- 当前值（测试数 / 步数 / 台账条数 / 证据档位）**全部从 `claims_v0.json` 读**，判据不硬编码；
- **禁止写死 commit hash**——hash 每次提交都变，写进展示页必然过期，统一指向 `git log -1`；
- 华为关联页、`鲲鹏未实测`、`③ 档不计已验证` 是必检项，删了就 FAIL；
- 页码与 section 数必须一致；与仓库外副本逐字节比对只在本机存在时执行，CI 上如实跳过；
- 7 例双向断言（旧值回填 / 删边界 / 写死 hash / 页码不符都必须 FAIL）。

展示页同时扩为 11 页，新增第 10 页「华为关联 · 可复算证据」；
旧 10 页 PDF 按纪律保留为历史快照，不回填。

> **这一层不进 ① 档吗？进。** C22 是 ① 档，探针当场跑命令。
> 但必须写明：判据只读仓库内文件、不联网（CI 上不依赖网络）。
> 线上 Pages 由**本仓库的 `gh-pages` 分支**发布，逐字节比对交给
> `python3 scripts/publish_pages.py --check`（本地 ② 档工具）。
> 2026-11-09 已同步，线上与本地 sha256 一致。
>
> **一次误判，留案**：上一版这里写的是「部署源不在本仓库（Pages API 404），

> Pages API 对未认证请求不给元数据。两个信号叠在一起，把「没查清」当成了

### 5.5 一条「更接近、但仍不是」的证据

C23 记录 Linux aarch64 原生 runner 上跑通。写进台账时有个诱惑：
能不能顺手把 C18「鲲鹏实例未实测」改成「已验证」？**不行。**

- 存档 `data/aarch64_linux_v0.json` 带三条边界声明，少一条判据 FAIL；
- 判据同时校验 runner 必须是 `ubuntu-24.04-arm`、job 必须是 `aarch64-linux`，
  拿 x86_64 或其它 job 的记录冒充会 FAIL；
- 指纹必须与 macOS 存档一致，改一个字节就 FAIL。

所以 C18 仍是 ③ 档声明，③ 档欠账依旧 3 条。
C23 是 ② 档读档（证据是 CI run 记录，不是本地重算），
联网核对由 `scripts/verify_aarch64.py --check` 负责，CI 上不跑它以免限流。

> 这条的价值不在「多了一个绿勾」，在于**分得清「更接近」和「已经是」**。
> 答辩时这句话可以直接用：我们做到了 Linux aarch64 原生跑通，
> 但没有说它是鲲鹏——因为评测现场没人会给你一台鲲鹏。

### 5.6 判据抓到自己的第三个洞：身份字段游离在哈希外

账本上线的同一天，我回头审自己的代码，发现 `dedupe_key`（条目身份）
是**在算完 hash 之后**才写进条目的——改它，链照样绿。实测确认。

「这条记录是谁」本身就是主张的一部分；身份可以悄悄改掉，
防篡改就是半成品。修复：`dedupe_key` 进哈希体，`verify` 重算时带上它；
回归测试锁死（改 `dedupe_key` 必须 FAIL），仓库账本重建。

这和 C14（拿 x86 盖 arm64 的章）、浅克隆断言是同一类错误：
**判据不是免检的，写判据的人更要被自己的判据审。**

### 5.7 公开锚点与 Skill 功能层（2026-11-09 晚）

**公开锚点**：L2 的前两步本来要 clone 仓库。`publish_pages.py` 现在把
链头 + 6 条摘要生成 `verify/anchor.json` 推到 gh-pages，任何人 curl 即可对照；
`verify_bundle.py --anchor-url` 把它接进 L2（默认不联网，显式传 URL 才启用）。
**边界照旧**：公开锚点是包外的第三个对照点，不是信任根——
信任根仍是 git 历史与两个远端；能改仓库的人也能改这个文件，
但那需要一次可见的 push，与悄悄改审计包不同。

**Skill 功能层**：官方 `huaweicloud-skills` 的验收分结构 / 注册 / 功能 / 结果
四层，我们此前只做了结构 + 文档（18 项）。补两项功能层：
AC-18「SKILL/references 引用的每条命令目标都存在」、
AC-19「引用的仓库内文档都存在」——「文档里写着一条命令、仓库里没有这个文件」
是 Skill 最常见的腐烂方式，它看起来像规范，跑起来是空头支票。
双向断言 8 → 10 例，验收 18/18 → **20/20**。

### 5.8 第四、第五次自纠：公开锚点漏检与 Merkle 算法坑

2026-11-10 回头审前一天刚上线的公开锚点，又抓到两处：

- `--check` 只比 `seq/head/entries`，**改一条摘要也判 PASS**（实测复现）；
- L2-c 没检查 `head` 是否等于末条、`merkle_root` 是否由摘要算出。

修法是两端共用 `validate_public_anchor()` + 全字段逐条比对。
接着按 RFC 6962 / Sigstore Rekor 加 Merkle 包含证明时，
单测又抓到两个算法坑：审计路径方向（自底向上，n=3 起算错根）、
`tree_size` 不由证明单独绑定（6 叶改 5 仍算出同一个根）。
后一条的攻击用例**留在套件里没删**，只是补上外部 `seq` 约束。

到这里，「判据抓到自己」已经五次：C14 的架构误标、浅克隆断言、
dedupe_key 游离在哈希外、公开锚点两处漏检、Merkle 两个算法坑。
把它们都写在这里，比只留一行「全绿」有用得多。
