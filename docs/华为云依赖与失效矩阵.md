# 华为云依赖与失效矩阵

> 用途：证明「云原生」不是堆服务，而是**每个依赖都想过它不在了怎么办**。
> 口径：2026-11-07 当前 HEAD｜308 测试｜19 步自检全绿｜主张台账 22 条 / 0 违规

---

## 一、为什么要有这份矩阵

「我们接入了 RDS / Redis / MaaS / OBS」这句话本身没有信息量——
谁都能在代码里写一个客户端然后不连。

真正能说明工程能力的是另一句话：**「其中任何一个挂了，系统会变成什么样，用户会看到什么，怎么恢复。」**

这份矩阵就是那句话的展开。它同时解决一个尴尬问题：
有几个服务实例没开通（余额、订阅、额度），与其含糊带过，不如把"没开通时系统怎么表现"写清楚。

## 二、依赖矩阵

| 服务 | 依赖面 | 代码位置 | 不可用时系统怎么表现 | 用户看到什么 | 恢复动作 |
|---|---|---|---|---|---|
| **RDS for PostgreSQL** | 审计摘要、单据、判定指纹、反馈落库 | `src/store.py` | 自动降级 SQLite（同一份 schema），数据落在本地文件 | `/health` 显示 `db: {"backend":"sqlite"}`；`/history` 仍可查 | 配 `DATABASE_URL` 重启 |
| **DCS for Redis** | 结果缓存、IP 限流、异步任务状态 | `src/cache.py` | 降级进程内缓存；限流退化为单进程 | `/health` 显示 `cache: {"backend":"memory"}` | 配 `REDIS_URL` 重启 |
| **ModelArts Studio（文本）** | 表达层：结论 → 业主能问出口的话 | `src/llm.py` | 退回规则模板生成；**不伪造"AI 生成"** | 报告页标注「规则模板生成」 | 配 `MAAS_API_KEY` |
| **ModelArts Studio（视觉）** | 感知层：照片 → 结构化行项 | `src/perception.py` | 该 provider 不可用，提示切换 `file` / `ocr_table` | 上传页显示当前可用 provider | 同上 |
| **华为云 OCR「通用表格识别」** | 感知层：表格结构还原 | `src/perception.py` | 返回 401 / `ModelArts.4204` 时**明确报错**，不返回空表 | 错误文案带原因（未订阅 / 签名失败） | 控制台订阅服务 |
| **OBS** | 永久静态托管（复验页、回放页） | 无（静态文件） | 页面 404 | 材料里给出 GitHub Pages 备用地址 | 换 AK 重传 |
| **ECS + Nginx** | HTTPS 公网入口 | `deploy/nginx.conf`、`deploy/*.service`；IaC 见 `.auto-deploy/terraform/`（本地，gitignore） | 服务不在线；**判定链路不受影响**（引擎零依赖、不联网） | 本地 `uvicorn main:app` 可完整演示；复验页走 GitHub Pages | 有余额再开；`Ecs.7000` 是余额问题，不是代码问题 |
| **CodeArts 码道** | 开发过程留痕（五环节） | `.codeartsdoer/AGENTS.md` | 不影响运行时 | — | — |

### 三条设计纪律（这才是"云原生"的实质）

1. **失败可以降级，但 `/health` 必须说实话。**
   不假装连上——降级了就说降级了，`db` 和 `cache` 会如实报 `sqlite` / `memory`。
   一个在 `/health` 里撒谎的系统，没法被任何人信任。

2. **感知层失败要报错，不许返回空表。**
   扫描件没有文本层、OCR 未订阅、图片模糊——都明确报原因。
   返回空表最危险：用户会以为"这份报价单没有项目"。

3. **表达层失败退回模板，但要说清来源。**
   报告里"规则模板生成"和"MaaS 生成 · 已接地校验"是两句不同的话，不能混。

## 三、AI 能力层的真实状态（分级，不合并）

| 能力 | 状态 | 证据 |
|---|---|---|
| `file` 解析（CSV/XLSX/PDF 文本层） | ✅ **已跑通 5 份真实单据** | 603 行工序明细的评测全部基于它 |
| 本地 OCR（macOS Vision） | ✅ **已实测**，图片不出机器 | `src/vision_ocr.py` + 7 个单测 |
| 华为云 OCR 表格识别 | 🟡 **签名流程已打通**，服务未订阅 | 返回 `ModelArts.4204 The API ... is not subscribed`——是服务侧未开通，不是代码问题 |
| MaaS 文本/视觉 | 🟡 **代码就绪**，Key 未开通 | `src/llm.py` 接地校验有 9 个单测；报告如实标"规则模板生成" |
| 照片端到端 | ❌ **未跑过真机全链路** | 有额度即可补，链路已就绪 |

> 一句话口径：**我们卡在额度和订阅，不是卡在实现。**

### 已踩过的两个具体坑（写在代码注释里）

1. **AK/SK 手工签名的规范化 URI 必须带尾斜杠**，否则 401。
   用 `SDK-HMAC-SHA256` 手写签名时容易漏，这是华为云 OCR 的接口约定。
2. **`not subscribed` 与「签名失败」是两个不同错误**，不能混为一个"调用失败"。
   前者是商务/订阅问题，后者是代码问题——诊断必须分开，否则会往错误的方向修一天。

## 四、硬件层：ARM64 的真实证据与边界

### 已证实的

| 项 | 值 |
|---|---|
| 开发与全量自检的运行架构 | **arm64**（`macOS-26.6-arm64-arm-64bit-Mach-O`） |
| 判定引擎 `src/pipeline.py` | **零第三方包**（标准库 + 同仓 `src/` 模块；由台账 C10 探针查导入） |
| 在该架构上跑完的验证 | **308 个单元测试 + 19 步自检全绿** |

**为什么"零依赖"和 ARM 有关**：
`numpy` / `torch` 这类库带编译好的 C 扩展，换架构要重新编译或换轮子；
纯标准库的 Python 代码不需要。所以判定引擎在 ARM64 上是**直接可运行**的，不是"移植过去的"。

### 没证实的（不写成成果）

- **IaC 实测用的是 x86 机型 `s6.large.2`，不是鲲鹏。** Terraform 用 `huaweicloud` provider 1.90.0
  在 `cn-north-4` 真的建出 VPC / 子网 / 安全组 / 密钥对，ECS 因 `Ecs.7000` 余额不足没建成。
  完整脱敏证据见 `docs/华为云IaC实测与硬件边界.md`。
- **我们没在鲲鹏实例上实测过。** 同为 ARM64 指令集，理论上可直接运行，
  但"同架构"不等于"已验证"——内核、glibc 版本、Python 构建方式都可能不同。
- **也没在昇腾上做过任何 NPU 相关工作**，本项目的模型调用全部走 API，不涉及本地推理芯片。

### 要补的话，成本很低

一台鲲鹏 ECS，跑一次：

```bash
git clone https://github.com/cwt66/zhuangmingbai.git && cd zhuangmingbai
python3 -m pip install -r requirements.txt   # 只有可选依赖
bash scripts/check_all.sh                     # 期望 [ALL GREEN]
```

输出贴进 `09_证据附录/运行存证/kunpeng_<date>.txt`，这条就从推论变成证据。
**在有这份输出之前，材料里只写"ARM64 已验证、鲲鹏未实测"。**

## 五、这张表已经变成可执行的了（2026-11-08）

上面八行以前只是文档。`eval/cloud_failure_matrix.py` 现在把每一行都做成
一次故障注入 + 一条断言，接进 `check_all.sh` **第 17 步**，台账 **C20** 锁住结果：

| 实验 | 注入什么 | 断言什么 |
|---|---|---|
| RDS / DCS / MaaS 文本 | 不可达地址、空 Key | 降级为 sqlite / memory / 模板，且 `health()` 如实说；HTML 写「规则模板生成」 |
| MaaS 视觉 / 华为云 OCR | 无凭据调 `perceive` | 抛 `PerceptionError`，不返回空表；源码无 `return []`，`not subscribed` 与「签名失败」分开 |
| OBS / ECS / CodeArts | 静态契约 + AST | 备用地址真写在材料里；判定引擎零网络导入；码道不进运行时 |
| **ALL-DOWN** | 8 个依赖同时置不可用 | 完整审计的判定指纹与核减金额**逐字节不变** |

再配 5 例双向断言：干净降级态必须 PASS，把 `sqlite` 撒成 `postgres`、
把 `memory` 撒成 `redis`、感知层改成静默 `return []`、两次指纹不一致——都必须 FAIL。

方法来自 GitHub 上的 `chaos_toolkit`（受控故障注入验证 fallback）、
`qa-resilience`（deterministic fault injection 先于 staged chaos）、
`resilience-pattern-engineer`（**每条声明的防御都要有一个 chaos test 证明它触发**）。
报告在 `out/cloud_failure_matrix.md`，一句话复现：

```bash
python3 eval/cloud_failure_matrix.py --self-test --json
```

> **边界**：注入的是本地不可达地址与空凭据，不是真把华为云实例关掉；
> 证明的是「代码在依赖不可用时的行为」，不是云服务的 SLA。

### 5.1 第一次上 CI 就抓到一个真 bug（这套判据不是摆设）

`b61395f` 推送后，GitHub Actions 两个 job 同时红，本机却全绿。
根因不是 CI 坏了，是**文档与实现不符**：本机没装 `psycopg`，
`Store._init_backend()` 直接走「驱动未安装 → SQLite」；CI 装了 `psycopg`，
于是 `kind="postgres"`，`_init_schema()` 连不上 PG 时把 `kind` 置为 `"down"`
（完全不可用），只写了句「已降级」的说明——**其实没有降级**。

矩阵承诺的是「自动降级 SQLite」，代码给的是「整个存储不可用」。
`exp_rds` 断言 `kind == "sqlite"` 把它顶了出来。

修法不是放宽断言，是修 `src/store.py`：PG 初始化失败时清掉 dsn、
按 SQLite 重建 schema、`degraded` 写清原因；只有 SQLite 也失败才置 `down`。
`exp_rds` 同时注入两种情况（驱动不可用 / 驱动在但初始化失败），
并用临时目录 + mock，**不连真库、不写项目数据、与 CI 是否预装依赖无关**。
本地用假模块复现 CI 依赖环境再跑一遍 17 步，`[ALL GREEN]`。

> 这一段是修复记录，不是撤回档案里的撤回结论，所以不进 `claim_history_v0.json`。
> 但它值得留在这里：**一个只在开发者机器上绿过的降级承诺，等于没有承诺。**

## 六、一句话总结

> 我们没有把"云原生"当形容词，而是把它拆成了三件可检查的事：
> **每个依赖都有降级路径、每次降级都在 `/health` 里说出来、每个失败都报原因而不是返回空。**
> 至于实例开了几个——RDS 开了，Redis 和 MaaS 还没，ECS 停在 `Ecs.7000`，这是事实，
> 也是这份矩阵存在的原因。相关证据与硬件边界见 `docs/华为云IaC实测与硬件边界.md`；
> 对外每句数字的复算口径见 `docs/CLAIM-LEDGER.md`。
