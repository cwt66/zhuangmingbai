# 服务器复验证据（Verification Attestation）

> 2026-11-10 新增。起因：服务器首次复验抓到一次**假通过**——
> git bundle 只含 `main`，clone 后 remote HEAD 指向不存在的 `master`，
> 工作区是空的，脚本却打印 `✓ 完成`、退出码 0。
> 「跑过了」不等于「主张成立」。这份文档把复验结论做成可复算的证据对象。

---

## 一、它解决什么

| 以前 | 现在 |
|---|---|
| 日志里一句 `[ALL GREEN]` 就当复验通过 | 证据里每条主张都要映射到日志的**具体行号** |
| 退出码 0 就是成功 | 退出码 0 不算证据；必须有 20 个步骤标记、`ALL GREEN`、无 `FAILED`、344 tests、台账违规 0、Merkle 12/12 |
| 日志被改一行看不出来 | `subject.digest` 绑定日志字节 sha256，改一个字节就 FAIL |
| 「在哪台机器跑的」靠口头说 | `runDetails.builder.id` 与 `externalParameters` 分开记录 |
| 「装了什么包」靠记忆 | `resolvedDependencies` 从 `--target` 目录的 `*.dist-info/METADATA` 逐个读出 |

**核心规则只有一条**：每条公开主张都必须能在本次日志里逐行复算；
日志字节变了、或任何一条主张找不到证据行，证据立刻作废。

## 二、数据结构（对标 in-toto / SLSA，但明确不是它们）

```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [{ "name": "check_all.sh 运行日志", "digest": { "sha256": "…" } }],
  "predicateType": "https://zhuangmingbai.local/attestation/server-reverify/v1",
  "predicate": {
    "buildDefinition": {
      "buildType": "…",
      "externalParameters": { "command": "bash scripts/check_all.sh",
                              "repo_commit": "…", "python": "3.12.3", "platform": "…" },
      "resolvedDependencies": [ { "name": "fastapi", "version": "0.162.2" } ]
    },
    "runDetails": { "builder": { "id": "self-hosted:linux:x86_64" },
                    "metadata": { "generatedOn": "…", "executionTime": "not_recorded",
                                  "invocationId": "…" } },
    "claims": [ { "id": "C-STEPS-20", "expect": "…", "reproduce": "…",
                  "hits": [ { "line": 1, "text": "== 1/20 语法编译", "groups": ["1"] } ],
                  "status": "pass" } ],
    "claimCount": 5,
    "limits": [ "…四条边界声明…" ]
  }
}
```

借用的三个结构点（**方法 borrowed，不宣称原创**）：

1. **in-toto Statement v1 / SLSA v1.2 provenance**：`subject` 用 digest 绑定产物；
   `buildDefinition.externalParameters`（外部给的命令与 commit）与
   `runDetails.builder`（平台自己给的执行者身份）分开，避免信任边界混淆；
   `resolvedDependencies` 记录本次运行实际解析到的依赖。
2. **verification-gate 类 Agent Skill**：只认 fresh evidence、禁止「Done!」式完成声明、
   exit code 不是证据、每条主张逐条映射到输出行。
3. **Agent Skills `testing` skill** 的证据形状：每条主张都带
   `expect` / `reproduce` / 观测值，而不是一句「通过」。

## 三、怎么复算（全部在服务器上跑）

```bash
# 0) 公开前确定性脱敏：只泛化服务器路径 / 主机名 / IP / 账号，
#    并断言 5 条主张的观测值逐字不变（原始日志不上传）
python3 scripts/verify_server_attestation.py --redact \
  --log  ~/zmb-tasks/results/T002_check_all.txt \
  --out  ~/zmb-tasks/results/server_reverify.log
python3 scripts/pii_scan.py --strict ~/zmb-tasks/results/server_reverify.log

# 1) 生成证据：读脱敏后的日志（builder 不含主机名 / 别名 / 账号）
python3 scripts/verify_server_attestation.py --build \
  --log  ~/zmb-tasks/results/server_reverify.log \
  --out  ~/zmb-tasks/results/server_attestation.json \
  --commit "$(git rev-parse HEAD)" \
  --builder "self-hosted:linux:$(uname -m)" \
  --deps ~/zmb-tasks/pydeps

# 2) 复算：重新读日志、重算每条主张、逐字比对证据
python3 scripts/verify_server_attestation.py --verify \
  --attestation ~/zmb-tasks/results/server_attestation.json \
  --log ~/zmb-tasks/results/server_reverify.log

# 3) 双向断言自测（已挂进 check_all.sh 第 16 步，无需真实日志）
python3 scripts/verify_server_attestation.py --self-test
```

**第三方只要 checkout 仓库就能复算**，不需要服务器：

```bash
python3 scripts/verify_server_attestation.py --verify \
  --attestation data/server_attestation_v0.json \
  --log data/server_reverify_20261111.log
```

`--self-test` 用一份合成日志，验「干净必须 PASS」+ 7 招故障必须 FAIL：
删步骤标记 / 删 `ALL GREEN` / 测试数改 0 / 塞入 `FAILED` /
日志追一行（digest 失配）/ 篡改主张证据行号 / 篡改 `subject.digest`。
**一个永远判 PASS 的校验器和一个永远判 FAIL 的校验器一样没用。**

## 四、五条主张与它们的证据来源

| ID | 主张 | 日志里的证据 | 复算命令 |
|---|---|---|---|
| `C-STEPS-20` | 20 步全部执行、编号恰为 1..20 | `^== (\d+)/20 ` 的全部命中行 | `bash scripts/check_all.sh` |
| `C-ALLGREEN` | 自检自己判定全通过 | `[ALL GREEN] 全部检查通过。` | 同上 |
| `C-UNITTESTS` | 测试规模 ≥ 340 | `Ran 344 tests in …` | `python3 -m unittest discover -s tests` |
| `C-CLAIMS-LEDGER` | 主张台账违规 0 | `主张 25 条 / 违规 0 /` | `python3 scripts/claim_ledger.py --self-test --json` |
| `C-MERKLE` | Merkle 包含证明 12/12 | `Merkle 12/12` | `python3 eval/ledger_chain.py --json` |

额外的全局拒绝规则：日志里出现 `FAILED (` / `Traceback` / `ERROR:` 直接作废，
即使 `ALL GREEN` 也在——防止「后面补一句漂亮结论」把失败盖过去。

## 五、边界（必须和证据一起读）

- **没有签名**：不是 DSSE / Sigstore / cosign，任何能改仓库的人都能重造这份 JSON。
  它保证的是「日志字节没变 + 主张能在日志里逐行复算」，**不是**「第三方无法伪造」。
- **不是 SLSA L3**：builder 是自建 x86_64 服务器 `<host>`
  （Linux 6.14 / glibc 2.39 / Python 3.12.3），不是隔离的托管 CI，
  也没有受保护的 `attestations.write` 身份。**它不是华为云鲲鹏或昇腾机器**，
  不能拿来支撑「国产化硬件适配」类主张。
- **依赖未锁字节**：`resolvedDependencies` 只有 name / version，来自
  `pip --target` 的 `*.dist-info/METADATA`；没有 wheel 的 sha256、没有 lock 文件，
  因此不能证明依赖字节未被替换。要补这一步得引入 `uv.lock` / `pip-compile --generate-hashes`
  或 Sigstore 校验，本轮**没做**。
- **时间不可信**：日志里没有可信起止时间戳，所以 `executionTime` 明确写
  `not_recorded`；`generatedOn` 只是证据生成时间，**不冒充当次执行时间**。
- **公开的是脱敏日志，不是服务器原件**：`subject.digest` 绑定
  `data/server_reverify_20261111.log` 的字节；含服务器账号绝对路径的
  **原始日志留在服务器，不上传**。脱敏规则是脚本里公开的 `REDACT_PATTERNS`
  （泛化服务器路径 / 主机名 / IP / 账号），并断言 5 条主张的观测值逐字不变，
  所以「脱敏」不会被用来洗掉失败结论。
  重跑 `check_all.sh` 会产生不同字节（临时路径、耗时），**不能**用新日志复算这份旧证据。
- **builder 已脱敏**：证据里是 `self-hosted:linux:x86_64`，
  不含 SSH 别名、主机名、IP、端口、账号或任何密钥信息。
- **诚实差距**：in-toto 的 `subject` 通常绑定构建产物；我们绑定的是
  「运行日志」，属于证据对象而非交付物。真正对标 SLSA 需要对离线包 / 源码 zip
  做 subject 绑定，本轮未做。

## 六、与本轮其他发现的联动

`docs/服务器复验SOP.md` 原来写「20 步只有 Playwright 需要额外依赖」，
被服务器首次干净环境复验证伪：`test_web_gate.TestWebGateWiring.setUpClass`
无条件 `import main`，而 `main.py` 依赖 `fastapi`。本轮按实测修了 SOP 口径，
并把依赖清单写进 `resolvedDependencies`——**声明与实测从此在同一份证据里对账**。
