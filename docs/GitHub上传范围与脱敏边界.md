## 三、`deliverables/` 里有什么

| 文件 | 内容 | 复算命令 |
|---|---|---|
| `装明白_国奖提交包_2026-11-07.zip` | 11 分区完整提交包 | `shasum -a 256 deliverables/*.zip` 与 `deliverables/README.md` 比对 |
| `装明白_离线演示包.zip` | 纯代码离线快照（含 20 步自检可复算文件） | 同上；生成方式 `python3 scripts/build_offline_zip.py` |
| `README.md` | 交付物 sha256、生成时点、复算命令 | 本文件 |
| `装明白_评委复验页.html` | **当前版 11 页**，单文件零依赖；数字与台账绑定 | `python3 scripts/verify_showcase.py --self-test --json` |
| `装明白_评委复验页_11页.pdf` | 同一份 HTML 逐页渲染，11 张截图互不相同才落盘 | `python3 render_verify_pdf.py`（提交包 02 目录） |

> `gh-pages` 分支也在本仓库：`verify/index.html` 与 11 页 PDF 从这里发布，
> 2026-11-09 已同步到当前版（线上 sha256 `290bbd38…` 与本地一致）。
> 发布动作由 `scripts/publish_pages.py` 固化，`--check` 可只读比对。

**为什么允许「发布快照 commit ≠ 最终 HEAD」**：提交包是在某个 commit 上生成的；
之后为了把 zip 本身放进仓库，必然再产生一个同步 commit。
`scripts/verify_package_numbers.py` 因此接受快照 hash 落在最近 3 个祖先里，
但**任何无关 hash 仍然 FAIL**（`--self-test` 里有专门一例）。
这不是放宽口径：修的是「生成完再上传会误报自己过期」这个设计缺陷，
诊断与改动都写进了自检报告与方法论文档。

> 后续又被 CI 抓到一次：默认浅克隆只有 1 个 commit，`HEAD~1` 不存在，
> 新增的正向断言构造不出来。已把候选挑选抽成纯函数，
> 双向断言不再依赖 git 历史深度；用 `--depth 1` 浅克隆复现并验证通过。
> 细节见 `docs/CLAIM-LEDGER.md` §5.3。

## 四、隐私扫描结果（可复算）

```bash
python3 scripts/pii_scan.py --strict        # 代码仓：0 命中
```

对工作文件夹的文本层（`.md/.txt/.csv/.json/.html/.py/.sh/.yml`）逐文件扫描，
命中 7 处，逐条核对后**全部是误报或示例数据**：

| 命中 | 实际内容 | 判定 |
|---|---|---|
| 2 处「姓名」 | 中文词「上传」被姓名上下文正则误伤 | 误报 |
| 2 处「邮箱」 | 运行存证里的 git 远程地址 | 非个人信息 |
| 3 处测试与脚本 | 单测里的假号码 / 假邮箱 / 推送脚本示例地址 | 示例数据 |

**未被这份扫描覆盖的边界**：图片型真实单据、官方报名表 `.docx`、PPT 与视频等二进制，
没有做 OCR 级 / 元数据级复核，所以一律不进公开仓。
报名表 Markdown 备份里的个人身份栏目经人工核对**全部是方括号占位符**，无真实值。

> 结论：`deliverables/` 里两个 zip 的文本层无真实个人信息；
> **仓库外的原始素材不做「已脱敏」承诺**，只做「不上传」承诺。
