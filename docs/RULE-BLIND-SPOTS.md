## 一、我们为什么去测自己的规则

项目从第一天起就主张：**判断交给 13 条可逐条审阅的规则，不是硬编码 if-else**。
这句话是全部创新叙事的地基。但主张不会自己成立。

2026-11-07 把变异测试打在 `data/rules_v0.json` 上，第一次结果是：

| 指标 | 第一次 | 修完之后 |
|---|---:|---:|
| 变异数 | 47 | 47 |
| 被杀 | 18 | **35** |
| 杀死率 | 38.3% | **74.5%** |
| **判定字段存活** | **17** | **0** |
| 双向断言 | 通过 | 通过 |

「判定字段存活」的含义很具体：改了规则里的字段，结论一个字都不变。
也就是**那一栏配置是写给评委看的，不是给引擎读的**。

## 二、已修（17 → 0），且默认输出零变化

| 字段 | 原来的问题 | 修法 |
|---|---|---|
| `enabled`（13 条） | 全写着 `true`，但 `audit()` 一行都没读。改成 `false`，结论一条不少 | `audit()` 加 `on(rid)` 开关；`find_duplicates` / `cross_unit_mix` 内部也判 |
| `min_lines`（R3） | 规则写 2，代码硬编码 `len >= 2`。改成 99 毫无反应 | 从 `rule_same` 读，默认 2 |
| `strength`（R5） | `cross_unit_mix` 写死 `confidence=0.70, tier=review`，规则里的 0.7 是摆设 | 走 `confidence()`；默认算出来仍是 review 档 |
| `scope`（R5） | 写了 `cross_quote`，没人读 | 非 `cross_quote` 直接返回空 |
| `tolerance_pct`（R13） | 规则写 0.005，`reconcile()` 里另硬编码一份 0.005。改规则不生效 | `audit()` 里按规则重算一次 `ok`；默认值完全一致 |

**零回归验证**：224 tests OK；五份冻结指纹逐字节一致；
`auto` 精确率 / 召回率、86 条结论、可核减金额全部未变。
修的是「配置有没有被读」，不是「判定逻辑」。

## 三、仍然存活的 12 个变异：是预期，但要说清

12 个全是 `then.evidence.basis`——规则里写的**基准说明文案**。

- R13 是例外：`find_doc_recon()` 确实读了规则里的 basis，所以它的变异被杀。
- 其余 12 条的 `evidence.basis` / `formula` 在代码里是**带具体数值的动态串**，
  例如 `10×50=500，单列 800`。规则文件里写的是模板声明，例如 `T \ S`。
  两者不是替代关系：一个说「规则怎么定义」，一个说「这一行算出来是多少」。

**为什么没有强行绑定**：把代码改成读规则文案，会丢掉业主能用计算器核的那串数字；
给每条结论新增一个 `rule_basis` 字段则会改变 `snapshot_predictions` 的摘要对象，
牵动五份冻结基线。收益（多杀 12 个变异）小于代价（丢可核验细节 + 全链重冻）。

> 这不是「修不好」，是**权衡后不修**。活性报告里它们仍标为「存活」，没有偷偷改分类。

同理未做变异的声明性字段：`name` / `type` / `when` / `then.conclusion` / `then.severity`。
变异算子只覆盖单字段取值，没做类型级、跨字段或语义级变异——**算子有限，是边界**。

## 四、静态可达性：变异测不出来的另一类问题

变异测试改的是「值」，查不出「条件本来就不可能满足」。

R2 的触发条件要求 `container 不在模板 且 contained 在模板`，
但容器工序（贴地砖 / 贴墙砖 / 铲墙皮）本身也是模板必做项：

| 工艺对 | old_house | new_house |
|---|---|---|
| `tile_floor → grout` | ❌ 不可达 | ❌ 不可达 |
| `tile_wall → tile_corner` | ❌ 不可达 | ❌ 不可达 |
| `demo_putty → putty` | ❌ 不可达 | ✅ 可达 |
| `backfill → level_floor` | ✅ 可达 | ✅ 可达 |

共 **5 个（模板 × 工艺对）不可达配置**；两套模板下分别有 3 对、2 对永不触发。

**本轮不修。** 理由不是"没时间"，是纪律：

1. 修条件会新增重复计价结论 → 五份冻结指纹、`auto` 精确率 0.833、86 条结论全部要重算；
2. 现在只有**单一标注者、n=2**，新增结论没有第二个人复核；
3. 项目纪律是「宁可少报，不可错报」。在没有标注能力之前放宽触发条件，
   等于用未经验证的结论去换一个更好看的覆盖率数字。

要修，需要单独一轮：重冻基线 + 补标注 + 重新核算评测，并在提交说明里写明
「判定口径有意变更」。**不能用一次顺手的小改把它夹带进去。**

## 五、其它已知边界（工作流梳理时一并确认，均非本轮修复范围）

| # | 边界 | 影响 | 为什么暂不动 |
|---|---|---|---|
| 1 | `parse_q` 在 `confidence()` 的 15 处调用里恒为 0.95 / 0.98 | 解析质量从未进入置信度；`schema_parse.json` 定义的行级 confidence 未产出 | 让它真变化会改所有结论的档位与核减金额，需要重冻 + 重评 |
| 2 | 3 条规则在 5 份真实单据上从未触发（R10 / R11 / R12） | 只能说「构造样本验证可触发」，不能说「真实场景已验证」 | 需要真实含该类缺陷的单据，不是加规则能解决的 |
| 3 | `build_html` 的 `_quality()` 用严格 `diff == 0` 重算对账，与 `reconcile()` 的 0.5% 容差并存 | 同一份报告可能同时显示「对平」和「差额 X」 | 展示层口径统一，独立一轮 |
| 4 | `main.py` 的 Web 判定路由不经过 `report_gate` | 交付门只在 CLI / 脚本里跑 | 本轮已接线（见下） |
| 5 | `audit_one.py` 在 `verdict=block` 时仍输出全部结论并 `return 0` | 交付门是 advisory，与 `SKILL.md` 的「block 不给业主结论」冲突 | 需决定 CLI 契约，单独一轮 |
| 6 | `result_digest` 不覆盖 `obligations` / `pricing` / `addon_forecast` / `confidence` | 审计包 `[PASS]` 不能证明这些结论未被篡改 | 扩大摘要会改全部指纹，需重冻 |

## 六、这份清单怎么用在答辩上

不要说「我们测出 17 个缺陷并全部修复」——那是把候选当判决，正是原方法警告的做法。

正确的说法是：

> 「我们把变异测试打在自己的规则文件上。第一次 47 个变异只杀掉 18 个，
> 说明『13 条可审阅的规则』这个主张里有 17 处配置其实没接上。
> 修完之后判定字段存活为 0，杀死率 74.5%，**而且五份冻结指纹一个字节没变**。
> 剩下 12 个存活全是声明性文案，以及 5 个静态不可达的工艺对——
> 我们没有改分类去刷指标，也没有为了让报告好看去放宽触发条件。
> 清单在 `docs/RULE-BLIND-SPOTS.md`，是诊断，不是修复日志。」

**最有分量的不是 74.5%，是那个 38.3%。**
一个从没测过自己核心卖点的项目，没有资格把「可审阅」写进创新点。
