# 外部对标与创新点校准（2026-11）

> 目的不是「找几个项目背书」，而是回答三个问题：
> **哪些做法已经是行业共识（不能当独创讲）？我们真的不同在哪？我们还没有什么？**
> 所有对标对象都可在 GitHub 公开检索；只写仓库名与做法，不写个人联系方式。

## 二、逐条校准我们的七个创新点

| # | 我们的主张 | 同类是否已有 | 校准结论 |
|---|---|---|---|
| ① | 把装修报价归一到 119 概念 / 388 别名 | 通用发票/账单项目做的是**字段**归一，不做**工序语义**归一 | **仍属独立**：领域坐标轴是装修场景特有资产 |
| ② | 13 条可审阅规则裁决，不经大模型 | 已是 2026 同类项目**共识**（BillGuard / MarginLeak / 发票助手都这么做） | **不能当独创讲**。要讲的是程度：规则逐条可审阅 + 每条结论带行号/基准/公式 + 交付门能否决自己 |
| ③ | 判定指纹 + 审计包离线复算 + **哈希链账本** | Provenant 有签名回执与哈希链；SOC_Replay 有可复现构建 | **差距已补（2026-11-09）**：6 条真实单据入链、链头锚在链外、离线包三层校验；链级 8 招拦 7 招、包级 4 招全拦。仍不如 Provenant 的地方：没有签名回执（非对称签名），也没有评测集门禁 |
| ④ | 变异测试打自己的规则（47 变异杀 35） | 来自 `gatecheck`，非我们原创 | **方法 borrowed，执行是自己的**：判定字段存活 17→0、未修的写进盲点清单 |
| ⑤ | 主张台账：每条对外数字配命令、证据三档、撤回档案 | 同类项目普遍**没有**这一层（它们只保证代码可测，不保证宣传可查） | **真差异**。尤其「撤回档案 + 预测 MISS 永久保留」在同类里没见过 |
| ⑥ | 云依赖失效矩阵：8 个依赖逐个注入、全挂指纹不变 | 同类项目很少把「云挂了会怎样」做成可执行实验 | **真差异**，且直接服务华为云关联 |
| ⑦ | 跨环境确定性：12 变体 + arm64 ↔ x86_64 + Linux aarch64 原生 | SOC_Replay 做构建可复现，不做**判定结论**跨环境比对 | **真差异**：比的是结论不是产物字节，且把「鲲鹏未实测」拆成可复算的分层 |

### 一句话结论

> 七个创新点里，**②④ 是行业共识或借用方法，不能包装成独创**；
> **①⑤⑥⑦ 是真差异**；**③ 已补齐哈希链账本 + RFC 6962 包含证明**，
> 但仍缺签名回执、紧凑一致性证明与评测集门禁。
> 答辩时主动把这条分界线说出来，比把七条都吹成首创更可信。

## 三、上一轮写下的差距，这一轮怎么补的

2026-11-09 的版本里，这张表写着「③ 方向对但缺哈希链账本」。
补的过程没有把这条删掉，而是留在上面并标注「差距已补」——**因为差距被补上，不代表它没存在过**。

补的时候先做了一件不太体面的事：**把攻击真跑了一遍**。

```
删掉 templates_v0.json 里 3 个必做项 → 漏项 12 掉到 10
用包里引擎重算 digest 写回 result.json
python3 verify.py → [PASS]
```

上一版只校验输入哈希，`result.json` 里记的 `standards_sha256` 从来没被用过。
所以补的不是「再加一层校验」，而是把**记录真相的东西从被审的容器里拿出来**：
账本独立成 `data/ledger.jsonl`（哈希链），链头锚在 `data/ledger_anchor.json`，
包内给三层（文件完整性 / 结论一致 / 链内自洽），包外给 L2（对照仓库与 git）。

### 仍然不如同类的地方（不因为补了一条就消失）

| 项 | 谁有 | 我们 | 为什么不补 |
|---|---|---|---|
| 签名回执（非对称签名） | Provenant | 只有哈希链 + 锚点 | 密钥管理是另一个工程；哈希链 + 仓库锚点已能挡住「事后改一条」，签名解决的是「跨组织不可否认」，场景还没到 |
| 评测集门禁（公开 bench） | Provenant（BillAudit-Bench） | 5 份真实单据 + 2 份黄金标注 + 242 例注入 | 家装报价**没有**公开数据集；自建标注集会被质疑「自己出题自己判」，所以只作区间估计不作 SOTA 宣称 |
| 坐标级证据链接 | BillSathi | 行号 + 原文摘录 | 报价单多为 CSV/表格，没有 PDF 坐标层；照片端 OCR 未接真机 |

**这三条写在这里，是为了让「我们补上了账本」这句话不顺手变成「我们没有短板」。**

## 三、同类有、我们还没有的三件事（诚实差距）

| 差距 | 它们怎么做 | 我们为什么没做 | 是否值得补 |
|---|---|---|---|
| **哈希链审计账本** | Provenant：每条结论串上前一条的哈希，篡改一条整链断 | 我们只有单份审计包的 sha256 + `verify.py`，没有链式 | 值得，但要改审计包格式与 `verify.py`；本轮不做，写进路线图 |
| **坐标级证据链接** | BillSathi：点字段在 PDF 上画框 | 我们的证据粒度是**原表行号**，因为主链路是 CSV/表格，不是扫描件 | 场景不同。若将来做照片端到端，需要补 |
| **供应商历史价对比** | MarginLeak：按历史均价判异常加价 | 需要真实历史数据，我们没有 | 不做。没有可信数据源就不判，这是负向知识库 NA 系列的原则 |

> **不补的理由要写清楚**：不是「来不及」，是「补了会破坏现有边界」
> 或「没有可信数据源」。前者是工程取舍，后者是诚信底线。

## 五、复验证据的对标（2026-11-10 追加）

本轮新增 `scripts/verify_server_attestation.py`，把「服务器侧一次自检跑绿了」
变成可复算的证据对象。先查重，再写差异：

| 对标对象（2026-11 检索） | 它做了什么 | 我们借了什么 | **没做到 / 不能讲** |
|---|---|---|---|
| `slsa-framework/slsa` v1.2 + in-toto Statement v1 | `subject` 用 digest 绑定产物；`buildDefinition.externalParameters` 与 `runDetails.builder` 分离；`resolvedDependencies` 记录依赖 | 三层结构、命令/commit/执行者分栏、依赖清单 | **不是 SLSA 任何等级**：没有签名、builder 非隔离托管 CI、依赖只有 name/version 无 wheel 哈希 |
| `sigstore/cosign` + DSSE 签名 | 用 OIDC 身份签 attestation，第三方可验证不可伪造 | 只借了「证据该绑 digest」这一条 | **没有签名**，任何能改仓库的人都能重造 JSON |
| verification-gate 类 Agent Skill | 只认 fresh evidence；exit code 不算证据；禁止「Done!」；主张逐条映射输出行 | 「退出码 0 ≠ 主张成立」+ 逐行映射 + 7 招双向断言 | 我们绑定的是**运行日志**，不是构建产物；重跑日志字节不同，不能复算旧证据 |
| Agent Skills `testing` skill | 证据形状：lane / given-should-actual / reproduce command | 每条主张带 `expect` 与 `reproduce` | 没有人工审批门与交付收据链 |
| `charmbracelet/vhs` | 把终端演示写成 `.tape`，渲染成 GIF/MP4/WebM，可在 CI 重跑 | 「演示是源码」：8 镜写成剧本，改代码后重跑即更新 | 我们驱动浏览器不是终端；没有帧率/主题语言 |
| `AlexKay28/clickcast` | Playwright 录制 + JSON sidecar + **distilled assertions**（只比 step/状态/错误计数） | distilled 字段取舍：删墙钟、耗时、截图哈希，只留可跨机复算的结构 | 没做像素级 visual diff，也没自动编码成 GIF/MP4 |

**演示层的一句差异**：同类工具解决「怎么录」，我们多走一步——
**录出来的东西可以被下一个人用一条命令复算**（`scripts/auto_demo.py --verify`），
且明确只比结构不比像素。8 张关键帧同时是视频分镜底稿，
解决「改一版就要重录一次」的反复成本。

**触发它的真实缺陷**：2026-11-10 服务器初始化时，git bundle 只含 `main`，
clone 后 remote HEAD 指向不存在的 `master`，工作区是空的、脚本却打印
`✓ 完成` 且退出码 0。这正是 verification-gate 说的 "exit code matters,
but a zero exit code that only prints a warning is still insufficient"。
我们把这条教训写成了机器可拦的判据，而不是写进「经验教训」。

**仍然不如同类的地方（不因为补了一条就消失）**：

1. 无签名、无公开透明日志锚定，做不到 Sigstore / Rekor 那种第三方不可伪造。
2. `resolvedDependencies` 未锁字节；补法要上 `uv.lock` / `pip-compile --generate-hashes`。
3. 日志原件未随仓库公开，`subject.digest` 第三方拿不到同一份字节就无法复算。
4. builder 是自建 x86_64 服务器 `<host>`，
   **不是华为云鲲鹏 / 昇腾**，不能用来支撑「国产化硬件适配」类主张；
   五层硬件边界（macOS arm64 / Linux aarch64 / x86_64 / 鲲鹏未实测 / 昇腾未涉及）不变。

> 华为关联校准补一行：**服务器复验**这一维度上，同类常写「已在云端复现」，
> 我们写的是「自建 x86_64 服务器 + 依赖隔离目录 + 逐行可复算证据 + 明确不是鲲鹏」。
> 更诚实，但也确实**没有**华为云托管 CI 的可信执行环境，这是差距不是亮点。

## 六、这份文档怎么用

- **答辩**：被问「你们和 GitHub 上那些 invoice auditor 有什么区别」时，
  直接给第二节那张表：共识三条、差异四条、差距三条。
- **自查**：每次想加一个「创新点」前，先在这里查是不是别人已经做了。
  是共识就写「我们做到了什么程度」，不要写「首创」。
- **复算**：本文只做定性对照，不含数字主张；所有数字仍以
  `data/claims_v0.json` 与 `09_证据附录/评测数字总表.md` 为准。
